## 确认缺陷

### P1：真实生成的有限修复结局否认已经成立的修复事实

- 真实存档：`80a8d300-fc4c-44d1-b16f-60f509cdb033`。
- 结局 AI 任务：`f6b59833-d1f1-495f-b22b-c2718984a3fa`，完成且有真实 token 用量。
- 步骤：处理采购、澄清与交付 → 提出修复 → 承认伤害 → 实际补救 → 后续协作尊重拒绝 → 收束本局。
- 数据库/存档已记录 `friendship`、`harm`、`remedy`、`follow_up`，主结局为有限修复。
- 实际正文却写：“你与孙淼之间关于保留友谊、先谈清具体伤害的对话仍停留在你表达意愿的阶段，孙淼尚未回应。”
- 原因线索：`story_rules.py` 保留早期 `friendship_offer` 的“尚未回应”历史描述；`jobs.py:188` 把全部阶段事实平铺给模型，`jobs.py:428` 只校验正文结构，不检查其与当前有效事实是否冲突。
- 影响：结局标签正确，正文却否认玩家实际取得的成果；不能归为普通措辞差异。
- 修复方向：区分历史事件与当前有效状态，显式表达阶段先后；为结局生成添加关键事实一致性校验或可控降级。
- 证据：`artifacts/ending-audit/real-repair-contradiction.json`。

### P2：实际参加欢送会后，固定修复台词仍声称错过

- 步骤：第一幕申请加入名单 → 实际参加欢送会 → 后续完成有限修复。
- `farewell_attended` 已记录，但 `complete_remedy` 的历史文本仍写“已经错过的欢送会机会无法靠补发旧通知挽回”。
- 位置：`backend/app/story_rules.py:492`，对应补救事实也使用不分参加状态的描述。
- 桌面与手机均通过真实页面操作复现，`ending-edge-audit.spec.ts` 的正确性断言失败。
- 修复方向：依据是否参加选择补救描述；参加者只需纠正代替决定的做法，不应声称错失机会。
- 证据：`artifacts/ending-edge-traces-final/` 中 attending 场景的 trace、事件断言及截图。

### P2：退出申请提交成功后，重新打开人事页仍显示“尚未提交”

- 步骤：保存退出草稿 → 确认正式提交 → 进入主动转身 → 打开工作系统/人事申请。
- 存档中 `exit_draft.submitted=true`，但标题仍为“申请预览 · 尚未提交”。
- 位置：`frontend/src/features/v3/Work.tsx:263`，标题写死，未根据 submitted 投影。
- 桌面/手机均复现；后台申请没有丢失，是前端状态误报。
- 修复方向：区分草稿和已提交状态，终幕人事界面应正确显示只读结果。
- 证据：`artifacts/ending-edge-traces-final/` 中 submitted-exit 场景。

### P2：新故事真实 NPC 仍称主角为旧名字“周凌”

- 王会计实际回复以“周凌，材料你愿意提供，我可以帮你理一理流程”开头。

## 修复及最终回归

四项缺陷均已修复：

1. **P1 结局事实冲突**：生成输入区分当前有效事实与历史事件；已达成修复时不再将早期“尚未回应”作为当前事实。提示词明确阶段顺序，并对否认已记录的回应、承认伤害、补救、尊重边界和参会事实进行定向校验。仍使用原有两次调用上限，失败后展示已保存事实；没有改写历史台词或旧 AI 结果。
2. **P2 欢送会叙事**：实际参加过欢送会的玩家使用对应补救台词和事实描述；未参加路径保留原有语义。
3. **P2 申请状态**：提交后人事页显示“已提交”，区分提交记录与后续流程结果。
4. **P2 主角姓名**：NPC 提示词从故事定义读取姓名；新修订使用周菱菱，旧修订仍保留周凌。
