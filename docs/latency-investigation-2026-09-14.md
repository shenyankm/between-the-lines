# 响应延迟排查与优化（2026-09-14）

基线为 `15b7357`。本报告记录切换前的延迟排查；用户随后确认切换 DeepSeek，本地当前配置及验证见 [DeepSeek 接入记录](deepseek-gateway.md)。本次代码与报告提交到 `codex/ai-npc-integration` 分支。

## 实测

同一台机器、同一个 OpenAI Next 网关、同一段第一幕角色上下文、同一句问题；每次使用新的内存检查点与客户端，串行重复各三次。测试仅用合成对白，不读取玩家私聊。不同模型组并非严格同时实验，结果只代表这些样本，不能作为平均速度或 SLA。

| 模型及方式 | 三次整轮耗时 | 结果 |
| --- | --- | --- |
| GPT6 low，Responses | 27.5 / 50.6 / 50.5 秒 | 一次流读取超时，两次请求超时 |
| GPT-5.6 Luna none，Responses | 26.3 / 18.0 / 11.3 秒 | 全部完成；首轮发生重试 |
| GPT6 low，Chat Completions | 49.8 / 12.0 / 50.5 秒 | 两次连接/请求失败，一次完成 |
| DeepSeek V4 Flash 非思考，Chat Completions | 21.1 / 3.6 / 4.3 秒 | 全部完成；首轮发生重试 |

DeepSeek 使用网关 `/models` 实际返回的 `deepseek-v4-flash`，不是 DeepSeek 官方直连。这个网关的 DeepSeek 请求同样可能慢。三条回复都回应了玩家，但其中两条包含括号动作描写，与“只说角色对白”的要求有偏差；本次样本不足以替代完整角色质量验收。

网络恢复后，两次模型列表查询分别约 1.52 / 1.47 秒；本机没有代理环境变量。GPT6 的一个样本在本地准备约 184 毫秒、2.4 秒收到响应头，之后仍没有可显示正文，最终约 27.5 秒读超时。另一些失败甚至收不到响应头。证据说明等待主要发生在远端请求/正文返回阶段，客户端无法进一步区分网关内部排队、上游模型处理及其网络路径。

模型切换结论：DeepSeek 值得作为普通对白的候选，但不能保证每次几秒内完成。没有因为单组小样本就替换用户明确选定的 GPT6。官方直连仍需用户提供相应凭据后才能对比。

## 已实施的优化

- 已通过现有意图与权限校验识别出的材料、审核和项目支持请求，直接返回规则事务的真实结果。原来仅精确短语走快速路径，其他已识别同义表达还会调用模型复述；现去除这次冗余生成。拒绝办理仍返回真实原因，不捏造成功。
- 角色设定、事实、历史与行动信息保留；提示词 JSON 去除结构空白，降低重复传输与 token 开销。没有把删减事实当成提速手段。
- 添加每次生成独立的数值计时：准备、HTTP 请求开始/次数/字节、首个响应头、首个模型事件、首段公开文字和结束；回合另记录首段可见回复耗时。统计写入内部 usage/日志，不记录提示词、密钥或响应头内容，不扩大公开 API 契约。

本地浏览器对“请明确材料要求”实测：桌面约 **181 毫秒**出现结果，手机视口约 **79 毫秒**；后台分别 34 / 10 毫秒，模型调用均为 0。显示后刷新，回复仍在。该优化只适用于规则已明确识别的工作请求，**普通自由聊天仍受网关及模型等待影响**。
